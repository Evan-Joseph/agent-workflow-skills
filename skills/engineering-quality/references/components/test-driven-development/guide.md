# Test-Driven Development

## Use When

- 修复Bug，需要先复现失败行为。
- 修改核心业务逻辑、解析器、状态机、API行为、数据处理或权限流程。
- 用户要求测试、回归、验证、TDD、证明可用。
- 现有项目已经有测试体系，新增测试成本合理。

## Do Not Use When

- 只是改文案、排版、注释、README或简单配置。
- 项目没有测试体系且搭建测试会比任务本身更重；这时用最小可验证命令替代。
- 用户明确要求先快速原型验证。

## Workflow

1. 先查项目现有测试命令、测试框架和相邻测试，不另起一套体系。
2. Bug修复优先写最小复现；新行为优先写最小覆盖用例。
3. 如果无法写自动化测试，说明原因，并给出可重复的手工验证或脚本验证。
4. 实现改动后运行目标测试；必要时再运行相关lint、typecheck或构建。
5. 测试失败时先读失败信息和相关代码，不靠猜测连续硬改。

## Pragmatic Rules

- 不为了形式主义强行红绿重构；目标是可复现、可验证、可回归。
- 优先局部测试，收尾时再跑更大的回归集合。
- 不打印大体量日志或全量数据到上下文；只保留必要证据。

## Verification

- 有明确测试、命令、截图、日志或可重复步骤证明结果。
- 修改前后的行为差异能说清。
- 不能测试的部分要说明环境、依赖或权限限制。
