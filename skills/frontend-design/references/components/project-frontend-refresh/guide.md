# Project Frontend Refresh

这个Skill服务于“已有项目要翻新前端”的整套流程。

重点不是单独做设计，也不是单独做联调，而是把下面这些事情串成一条稳定工作流：

1. 先了解项目并跑起来
2. 再从代码和实际浏览里梳理现有前端
3. 产出给外部同事或AI的原型开发提示词
4. 接收用户提供的.zip前端原型
5. 在尽量不改视觉的前提下，直接替换旧前端并做真实联调
6. 测到每个控件和流程都是真实可用的
7. 规整项目结构并交付

## 与其他前端 Skill 的边界

把本 Skill 当成已有项目翻新的总入口。专项 Skill 按下面方式补位，不要并行抢 owner：

| 需求 | 路由 |
|---|---|
| 从零实现一个页面、组件或新前端应用 | `frontend-design` |
| 只做设计系统、视觉方向、UX 审查，不直接改代码 | `ui-ux-design` |
| 用户提供 Stitch 原型、Stitch prompt 或需要 Stitch 到 React 的交接 | `stitch-design` / `stitch-workflow` / `react-components` |
| 动画实现涉及 GSAP 时间线、React 集成或滚动触发 | `gsap-core` / `gsap-react` / `gsap-scrolltrigger` 作为专项参考 |
| 真实浏览器回归、控制台、网络、响应式截图 | `playwright` 或 `playwright-interactive` |
| 完成后做用户体验巡检、找粗糙细节和可用性问题 | `dogfood` |
| 性能、Core Web Vitals、Lighthouse、网络瓶颈 | `web-perf` |

所有真实浏览器回归都必须先加载 `browser-routing`。严格遵守零焦点抢占（无头优先或静默后台创建）、标签页进入命名任务分组（`[Agent] 任务名`）并默认折叠、优先原地复用标签页，中间页用完立即关闭，结束时执行清理回读并只保留明确的 deliverable 或 handoff，杜绝孤儿标签页；Playwright、DevTools 等调试路线由各自任务记录并关闭全部新建页面和进程。

如果任务同时包含“换 UI、接真实接口、清 mock、验证所有按钮”，继续由本 Skill 统筹；专项 Skill 只在相应步骤加载。

## 什么时候用

在这些场景触发：

- 用户要“前端翻新”“前端改版”“换一套新UI”
- 用户要先梳理旧前端，再交给别的团队或AI出原型
- 用户已经给了前端.zip，希望直接接入旧项目
- 用户要求保持新原型视觉不变，但把按钮、表单、列表、图表、地图、弹窗、导航等都接成真实逻辑
- 用户要求在联调完成后再整理项目结构、统一README并交付

这些场景不要硬套：

- 只做一个新页面的纯视觉改稿
- 只改局部CSS，不涉及原型替换和前后端联调
- 纯后端重构、纯数据库设计

## 工作原则

- 默认先看本地代码、配置、目录、环境变量和Git状态，再决定怎么动。
- 默认先把项目跑起来，再讨论前端到底长什么样、缺什么、要不要换。
- 前端梳理不能只读代码，必须配合实际浏览和交互验证。
- 用户给了.zip原型后，默认把它当成新的主线前端，旧前端转入`legacy/`或其他归档位置。
- 联调阶段不能接受模拟数据、假按钮、死链接、演示态表单、只会弹toast但不落数据的交互。
- 每个保留下来的控件都要满足二选一：真实可用，或者直接删掉。
- 任何翻新、接入或回归测试中，只要界面显得粗糙、不顺、廉价、AI感、像demo，或涉及按钮、卡片、导航、表格、图片、动态数字、切换态、进入/退出动画，必须读取`$HOME/.agents/skills/frontend-design/references/components/ui-ux-design/references/ui-polish-microdetails.md`并把相关检查并入验收。
- 只要用户没明确要求保留旧结构，就优先收敛成一个标准的`backend/ + frontend/ + docs/ + legacy/`结构。
- 全程维护本地Git，关键阶段必须提交。

## 必走流程

按顺序执行。用户只要停在某个阶段，就做到该阶段为止。

### 阶段A：接手旧项目

1. 查目录、运行方式、环境变量、端口冲突、Git状态。
2. 把项目在本地跑起来，至少确认：
   - 后端端口
   - 前端端口或托管地址
   - 登录页或首页是否可访问
3. 如果有端口冲突，选一个本机空闲端口，不要硬占系统端口。
4. 把实际可用的运行命令记下来，后面会写进README和最终交付说明。

### 阶段B：梳理当前前端

必须同时做两件事：

- 读代码
- 实际浏览

输出一份中文Markdown，默认放在`docs/`下，文件名建议用：

- `前端页面梳理.md`

梳理时不能只写“有什么页面”，至少要覆盖：

- 页面入口和路由
- 页面用途
- 主要内容块
- 每个主要按钮、筛选器、表单、弹窗、分页、切换、地图、导航、上传、分享等交互
- 数据来源和对应接口
- 鉴权要求
- 加载态、空态、错误态、禁用态、选中态、展开态、弹窗态
- 明显的移动端/桌面端差异
- 视觉与交互质感：文字换行、同心圆角、光学对齐、阴影/描边、图片边缘、命中区域、hover/press/focus、动态数字、动画可中断性
- 当前哪些逻辑是真实的，哪些还是本地存储、模拟数据或占位逻辑

模板见：

- `templates/前端页面梳理模板.md`

### 阶段C：给外部原型开发方写提示词

在梳理文档基础上，输出一份可直接给同事或AI使用的原型开发提示词。

默认也写成Markdown，建议文件名：

- `前端原型开发提示词.md`

这份提示词必须明确：

- 项目定位和目标
- 必须包含的页面
- 每页必须包含的内容块
- 必须覆盖的状态
- 视觉要求
- UI polish约束，至少覆盖文字换行、同心圆角、光学对齐、阴影/描边、图片边缘、命中区域、动态数字、hover/press/focus、动画节奏和响应式不溢出
- 不要做什么

另外补一条硬约束：

- 默认只写需求本身，不写和具体AI前端工具绑定的流程要求、输出格式、源码说明、zip打包、信息架构说明、组件清单、步骤列表等额外指令，除非用户明确要求。
- 原型提示词要尽量工具中立。无论对方用的是 v0、Lovable、Bolt、Antigravity、Claude Code、Codex 还是别的工具，提示词都应该主要约束页面、状态、交互和视觉，不要约束它“应该输出什么材料”。

模板见：

- `templates/前端原型开发提示词模板.md`

### 阶段D：接收.zip原型并落地

用户给了.zip后：

1. 转存到工作区合适位置，重命名成稳定文件名。
2. 解压并了解：
   - 技术栈
   - 运行方式
   - 路由和页面结构
   - 依赖和环境变量
   - 静态资源、图标、字体、图片
3. 评估它和现有后端能力的映射关系：
   - 能直接接的
   - 需要改前端适配的
   - 需要补后端的
   - 用户明确要求删除的页面或逻辑

### 阶段E：替换旧前端并做真实联调

这是核心阶段。

要求：

- 以用户给的原型为视觉主线
- 尽量不改视觉和交互布局
- 允许改前端实现方式
- 必要时改后端接口、数据结构和持久化逻辑
- 如果原型本身有粗糙细节，可以在不改变产品结构和视觉方向的前提下做UI polish修正；这类修正要能落到具体CSS/组件属性，不接受只说“更高级、更精致”。

这里必须逐项清理这些问题：

- mock数据
- demo文案
- 假跳转
- 假按钮
- 本地假状态
- 不落库的“保存成功”
- 只演示不工作的地图、播放器、搜索框、分页器、对话框、筛选器

验收标准只有一条：

- 用户能点到的东西，要么是真实可用的，要么被删掉了。

### 阶段F：浏览器回归测试

优先用浏览器或可验证的页面检查，不要只靠读代码自证。

至少覆盖：

- 登录、注册、退出
- 主要导航
- 核心页面
- 核心表单
- 每个关键按钮
- 成功路径
- 错误路径
- 空态/无数据态
- 关键第三方能力，比如地图、外链、上传、播放器
- UI polish回归：文字无明显孤行/挤压，嵌套圆角协调，图标和文字视觉重心正确，卡片/按钮/图片边缘干净，小控件命中区域足够，动态数字不抖动，没有`transition: all`或`will-change: all`

如果遇到外部依赖缺失，比如地图Key、第三方服务额度、账号权限：

- 先完成能完成的部分
- 再把缺什么、怎么补、补完后验证什么写清楚

### 阶段G：整理结构并交付

默认目标结构：

```text
.
├── backend/
├── frontend/
├── docs/
├── legacy/
└── README.md
```

这里要做的事：

- 旧前端转入`legacy/`
- 新前端收敛到`frontend/`
- 后端收敛到`backend/`
- 分析文档、提示词、检查材料收进`docs/`
- 根目录只保留一个README
- 运行方式、环境变量、目录说明、交付说明都写进根README
- 交付前把UI polish发现或修改写进`docs/回归测试记录.md`或最终汇报。只列真实检查项和真实修改，不写空泛审美评价。

## 交付物

默认至少交付这些东西：

1. 中文前端梳理Markdown
2. 中文原型开发提示词Markdown
3. 已接入的新前端代码
4. 已联调的后端代码
5. 回归测试结论
6. 最终README
7. Git提交记录

## 推荐命名

- `docs/前端页面梳理.md`
- `docs/前端原型开发提示词.md`
- `docs/联调记录.md`
- `docs/回归测试记录.md`

## Git要求

- 接手项目并跑通后，可以先做一次初始化提交
- 页面梳理和文档产出通常不必单独提交，除非用户要求
- 原型接入前后各至少一次提交
- 关键修复、地图/鉴权/持久化/结构重组后各有独立提交更好
- 不要用破坏性命令覆盖用户工作区改动

## 最终汇报必须包含

- 当前做到哪个阶段
- 项目现在怎么跑
- 哪些功能已经是真实可用的
- 哪些能力还受外部依赖限制
- 关键文件位置
- 如果做了结构重组，新结构是什么
